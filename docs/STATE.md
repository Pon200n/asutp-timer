### Найденный и исправленный дефект: восстановление после перезагрузки

Проверка на телефоне показала: после `adb reboot` **до разблокировки экрана
будильников нет вообще** — а это ровно тот режим, для которого всё и делалось
(телефон лежит заблокированным). Причин было две, и обе снимались только вместе:

1. **Не было `android:directBootAware`.** Система шлёт `LOCKED_BOOT_COMPLETED`
   ещё до разблокировки — но компоненту без этого флага она такую доставку
   не делает. В логе было видно, что процесс после загрузки поднял плагин
   `local-notifications` (у него `directBootAware=true`), а наш приёмник
   в той же посылке не отработал.
2. **Расписание лежало в credential-encrypted хранилище** (`/data/user/0`),
   которое до разблокировки зашифровано: `run-as` отвечал
   `couldn't stat /data/user/0/com.asutp.timer`. Читать было нечего, даже если
   бы приёмник запустился.

Исправление (#43):
* `directBootAware="true"` — у `AsutpBootReceiver`, `AsutpAlarmReceiver`,
  `AsutpLiveService`;
* расписание и очередь событий переведены в **device-protected** хранилище
  (`createDeviceProtectedStorageContext()`) — доступно всегда;
* восстановление выполняется **один раз за загрузку** (по `boot_count`):
  `LOCKED_BOOT_COMPLETED` приходит до разблокировки, `BOOT_COMPLETED` и
  `USER_UNLOCKED` — после; второе пересоздание будильников сдвинуло бы их
  в очереди Doze (регресс +15 с);
* страховка `ACTION_USER_UNLOCKED` + `try/catch` вокруг TTS (на
  заблокированном телефоне движок речи может не подняться — зуммер включит
  семисекундная страховка).

**Ограничение, о котором надо помнить:** пока телефон заблокирован, голос может
не прозвучать (движок TTS не поднимается в direct boot) — сигнал, вибрация и
полноэкранное уведомление работают.

## 1. Задача

**ASUTP Timer** — приложение для инженера/оператора АСУТП, ведущего смену по
шаблону технологических блоков. Оно должно:

* вести расписание операций смены (шаблоны → рабочая очередь → копия в смену);
* в заданный момент **будить телефон и оповещать** о начале/конце операции;
* корректно вести себя при **регламентных перерывах** (пауза/возобновление);
* выдерживать смену в фоне, с выключенным экраном и в беззвучном режиме.

Эталон — веб-прототип `cyber_asutp_v8_stable.html` (стиль «Night City HUD»,
пользовательская оценка 89% — сохраняем без изменений). Эталонный ТЗ —
`TZ_ASUTP_Shift_Timer_v2.pdf` (в репозитории не лежит, лежит у автора).

## 3. Как реализовано пробуждение — полная цепочка

Это ключевая часть: **требует ли приложение быть живым, чтобы разбудить телефон?**
Нет. Будильник ставит **операционная система**.

```
Пользователь жмёт «ЗАПУСТИТЬ СМЕНУ»
   │
   ├─ App.Shift.start() → App.Shift.rebuild()
   │     └─ App.Scheduler.calculate(chain, shiftStartMs, now)
   │          → плоский список событий: {id, atMs, title, text, kind, mode, …}
   │            (время в целых секундах, перерывы режут операции на части)
   │
   ├─ App.Alerts.buildShiftAlerts(events, shiftStartMs)
   │     → список ТРЕВОГ с id вида 11+index*10+№
   │
   └─ App.Native.scheduleAlerts(alerts)
         └─ AsutpAlarmPlugin.scheduleAlerts()   ← НАТИВНЫЙ ПЛАГИН
               AlarmManager:
                 • ближайшая тревога  → setAlarmClock()      (не откладывается в Doze)
                 • остальные          → setExactAndAllowWhileIdle() (точные, +WAKE_FROM_IDLE)
               ⇒ системные будильники, точные, с wakelock

        ─ время пришло (экран выключен, приложение убито) ─

AlarmManager → AsutpAlarmReceiver.onReceive()   ← процесс ОС поднимает приложение
   ├─ сохраняет тревогу в очередь (SharedPreferences) — чтобы JS подхватил,
   │  даже если приложение только что поднялось и плагина ещё нет
   ├─ Notification (id 4243, канал asutp_alarms_v3, IMPORTANCE_HIGH):
   │    • FullScreenIntent → система открывает MainActivity ПОВЕРХ блокировки
   │    • кнопка «ПРИНЯТО / ДАЛЕЕ» → BroadcastReceiver → ACTION_ACK
   ├─ AlarmSound.start() → MediaPlayer (res/raw/asutp_alarm_loop.wav)
   │    с AudioAttributes(USAGE_ALARM) → звучит В БЕЗЗВУЧНОМ режиме,
   │    бес��еровно, пока не подтвердили; + системный Vibrator
   └─ AsutpVoice.speak() → TextToSpeech с USAGE_ALARM:
        голос произносит текст события ОДИН РАЗ, и только после его окончания
        стартует бесконечный зуммер (ТЗ п.5.3)

        ─ приложение поднялось ─

JS: App.Native.init() → подписка на alarmFired / alarmAction
   → App.Alerts.onNativeAlarm() → очередь → showOverlay()
   → ЭКРАН ТРЕВОГИ: div #alarmOverlay (полноэкранный, z-index 9999,
     красная рамка, мигающая подложка) с кнопкой «✔ ПРИНЯТО / ДАЛЕЕ»

   Если приложение было убито и поднялось по полноэкранному намерению:
   очередь из SharedPreferences забирает App.Native.pollPendingAlarm()
   (при старте + раз в 4 с) → то же самое, но с задержкой 1–2 с на загрузку WebView.
```

### Почему именно так

| Решение | Причина |
|---|---|
| Будильники ставит ОС, а не JS-таймер | WebView в фоне засыпает, MIUI его выгружает — JS-таймер не гарантирует пробуждение |
| `setAlarmClock` для ближайшей тревоги | Единственный API, не откладываемый в Doze; в статус-баре видна иконка будильника |
| `setExactAndAllowWhileIdle` для остальных | Точные, с wakelock; задержка в Doze минимальна |
| Будильники не пересоздаются при пересборке расписания | Пересоздание сдвигает будильник в очереди Doze → была задержка +15 с |
| `USAGE_ALARM` для звука и голоса | Обычные уведомления/медиа в беззвучном режиме глушатся |
| Зуммер стартует после голоса, а не одновременно | Иначе громкий будильник заглушает речь (ТЗ п.5.3) |
| Свой Foreground Service вместо готового плагина | Нужен системный хронометр (`setUsesChronometer`) и полоса прогресса — готовый плагин их не умеет |
| Уведомление тревоги — с фиксированным id | Иначе в шторке копится стопка (было 26 уведомлений) |
| У канала тревоги **есть звук** | MIUI прячет уведомления каналов без звука в секцию «Без звука» — уведомление тревоги было не видно |
| Расписание будильников — в **device-protected** хранилище | Обычное `/data/user/0` зашифровано, пока телефон заблокирован. После перезагрузки `LOCKED_BOOT_COMPLETED` приходит до разблокировки — и приёмник не смог бы прочитать расписание: тревоги пропали бы до первого касания телефона |
| Экран тревоги — JS-оверлей, поднятый нативным FullScreenIntent | Сохраняем единый дизайн HUD; нативный Activity можно сделать, если нужна независимость от WebView |

## 4a. Что выяснено про MIUI (важно для понимания поведения)

| Событие | Что происходит на телефоне | Чем проверено |
|---|---|---|
| **Свайп из «недавних»** | **теперь тревоги уцелеют**: приложение держит foreground-служба Live-Bar, и MIUI убивает только WebView-рендерер (`Renderer process crash detected`), но не процесс. Процесс уходит в фон, будильники остаются, при возврате в приложение JS поднимается заново и ничего не дублирует ✓. Раньше (без foreground-сервиса) это был `force-stop` (`description=SwipeUpClean`) — система отменяла все будильники | `dumpsys activity exit-info`, `dumpsys alarm` |
| **Перезагрузка телефона** | система будильники **не восстанавливает** (после `adb reboot` их 0 ✓). Восстанавливает наш `BOOT_COMPLETED`-приёмник — но **до разблокировки экрана не работал**: не было `directBootAware` + данные в зашифрованном `/data/user/0`. Исправлено и **проверено**: после ребута на заблокированном телефоне — `LOCKED_BOOT_COMPLETED: восстановлено будильников 5`, времена совпали с до-ребутными | `dumpsys alarm` до/после, `logcat` |
| **Экран тревоги на заблокированном телефоне** | в direct boot обычный `MainActivity` системе недоступен: было `Error: Activity class ... does not exist`, экран оставался тёмным. Теперь полноэкранное намерение ведёт на нативный `AsutpAlarmActivity` (`directBootAware`): телефон сам просыпается (`Waking up from Asleep`) и показывает тревогу над замком ✓ | `logcat` (`Waking up`, `RESUMED`), скриншот экрана |
| **Громкость** | звук и голос идут по **STREAM_ALARM** (`USAGE_ALARM` ✓) — слышны в беззвучном ✓, управляются кнопками в приложении ✓. На экране блокировки MIUI крутит кнопками громкость **звонка** ✓, поэтому будильник оттуда не регулируется | `media volume`, `dumpsys audio` |
| **Звук уведомления** | играл по STREAM_NOTIFICATION — на максимуме и не управляем ✗. Уведомление сделано бесшумным (`setSilent(true)` ✓), звук даёт только нативный зуммер | правка #39 |
| **Вибрация уведомления** | MIUI игнорирует: `Vibrate ignored, not vibrating for ringtones or notify for MIUI` ✓. Работает только собственная вибрация приложения | лог `VibratorManagerService` |
| **WebView в фоне** | JS-таймеры задумливаются примерно вдвое (тик 500 мс → реальные ~1000 мс) — на точность будильников не влияет (отсчёт ведёт система), но Live-Bar обновляется вдвое реже | интервалы `updateLiveBar` в логе |

## 5. Известные ограничения и открытые дефекты

1. ~~**Подпись сборок.**~~ **Исправлено**: в репозитории лежит постоянный
   отладочный ключ `keystore/debug.p12` (RSA-2048, алиас `androiddebugkey`,
   пароль `android`), на него переключён `signingConfigs.debug` в
   `android/app/build.gradle`. Все сборки подписываются им → обновление
   поверх работает (`adb install -r`), разрешения и настройки не слетают.
   *Проверено на устройстве 22.11:* `adb install -r` → `Success` ✓, снос
   больше не нужен; данные (цепочка, настройки) переживают переустановку —
   их возвращает бэкап MIUI ✓.
   *Риск:* приватный ключ в публичном репозитории — для личного приложения,
   ставящегося только по adb на один телефон, риск практически нулевой.
2. ~~Публикация APK в релиз~~ **исправлено**: ассет грузился на `api.github.com`
   вместо `uploads.github.com` → 404. Теперь APK лежит по открытой ссылке ✓.
3. **Экран тревоги = JS-оверлей.** Пока приложение поднимается и грузит
   WebView, оверлей появляется с задержкой 1–2 с. Нативный Activity спасёт.
4. **В шторке и в приложении показываются разные оповещения пары**
   (в шторке остаётся последнее — «нужно начать следующую», в приложении
   первое). Можно свести к одному тексту или развести по id.
5. **Звонок во время входящего вызова** не проверен.
6. **Часы/браслет**: уведомление зеркалится на Mi Band (текст + вибрация), но
   **кнопка «ПРИНЯТО» на часах не работает** — это умеет только Wear OS.
7. **Скорость реакции** после пробуждения: приложение поднимается системой,
   но WebView грузится не мгновенно.
8. ~~**Свайп из «недавних» отменяет будильники**~~ **фактически не отменяет**:
   приложение держит foreground-служба Live-Bar, и MIUI при свайпе убивает
   только WebView-рендерер, но не процесс. Тревоги остаются, при возврате
   в приложение восстанавливаются без дублей ✓ (проверено 22.11).
   Предупреждение в интерфейсе оставить — на всякий случай.
9. ~~**Перезагрузка телефона** отменяла будильники~~ **было**: до разблокировки
   экрана тревог не было вообще (нет `directBootAware` + зашифрованное
   хранилище). **Исправлено и проверено** (#43): приёмник `directBootAware`,
   расписание в device-protected хранилище, восстановление один раз за
   загрузку. После ребута на заблокированном телефоне — 5 будильников
   поднялись, первый сработал точно и вывел экран тревоги над замком ✓.
10. ~~**Тревоги отменённого плана оставались в системе**~~ **было**: карта
    расписания хранит только текущий план, и выпавшие из него будильники
    никто не снимал — они звонили со старым текстом (найдено 6 таких).
    Исправлено: нативная часть помнит все поставленные id (`armed`) и
    снимает лишние при перепланировке и при остановке смены ✓.
11. **Громкость будильника на экране блокировки не регулируется** — MIUI там
    всегда крутит громкость звонка. Регулируется из приложения или из
    Настроек → Звук → «Сигнал будильника» ✓.

## 8. Как повторяется цикл разработки

### Как понять, какая сборка стоит на телефоне

**Номер прогона CI — единый идентификатор сборки во всех местах.** Он берётся
из `github.run_number` и прокидывается в APK (`versionCode`, `versionName`
«1.0.N», `BuildConfig.BUILD_NUMBER/GIT_SHA/BUILD_TIME`):

| где | что видно |
|---|---|
| Actions | **Build Android APK #48** |
| Releases | релиз назван **«Build Android APK #48»**, в описании — коммит и время сборки, у файла подпись «Сборка #48 · 4ea07eb» |
| **В приложении** | карточка «07 // Настройки», строка внизу: `сборка #48 · 4ea07eb · версия 1.0.48 · собрано 23.11 21:44` |
| Система | Настройки → Приложения → ASUTP Timer → «версия 1.0.48» |

Плюс точная проверка «та ли сборка стоит» — по контрольной сумме APK:

```bash
adb shell "sha256sum \$(pm path com.asutp.timer | sed 's/package://' | tr -d '\r')"
sha256sum <скачанный APK>
```

Суммы должны совпадать; в отчёте сборки (ветка `build-info`, файл
`apk-info/apk-diagnostics.txt`) sha256 собранного APK тоже указан.

### Цикл

```bash
# 1. правка кода → коммит → пуш
git add -A && git commit -m "..." && git push origin main

# 2. CI собирает Debug APK (~2.5 мин), артефакт в Actions

# 3. APK на телефон: скачать ZIP в браузере телефона → распаковать
#    (или: CI публикует APK в релиз и я качаю его через adb)

# 4. установка без ожидания облачной проверки MIUI
C:/dev/tools-android/platform-tools/adb.exe uninstall com.asutp.timer
C:/dev/tools-android/platform-tools/adb.exe install <путь-к-apk>

# 5. диагностика прямо с телефона
adb logcat -v time | grep -iE "asutp|alarm"
adb shell dumpsys alarm | grep -B3 com.asutp.timer      # будильники
adb shell dumpsys notification --noredact | grep asutp    # уведомления
adb shell screencap -p /sdcard/s.png && adb pull /sdcard/s.png  # скриншот
```

**Служебные скрипты**: `npm run sound` (генерация звуков тревоги),
`npm run vendor` (обновление бандлов плагинов), `npm test` (проверка
согласованности id тревог между уведомлением и внутренней очередью).
